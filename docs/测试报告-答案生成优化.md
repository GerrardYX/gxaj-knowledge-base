## 二、测试场景与结果

### 场景1：精准查询 - "如何新签合同"

| 项目 | 内容 |
|------|------|
| **测试目标** | 查询"如何新签合同"时，只返回"新签合同"相关内容，不混入"续签合同"、"登录"等其他场景 |
| **预期结果** | 仅返回包含"新签合同"关键词的 chunk，相似度排名靠前的结果全部与新签合同场景相关 |

**代码分析结果**:

**分块策略**（`parser.js:226-243`）：
```javascript
const scenePattern = /(?=\n\s*\d+\.\d+\s*【?场景】?|【场景】|\n\s*\d+\.\d+\s*)/;
const scenes = text.split(scenePattern).filter(s => s.trim());
if (scenes.length > 1) {
  return scenes.map(s => s.trim()).filter(s => s);
}
```

- 场景分割正则 `scenePattern` 匹配 `数字.数字` 格式的编号（如 `1.1`、`2.3`）以及包含 `【场景】` 的行
- 如果文档格式规范，不同场景会被分割到不同的 chunk 中，新签合同与续签合同不会混在一起
- **风险点**: 如果文档中的"新签合同"和"续签合同"写在同一个小节下（如都在 `1.1 合同管理` 下），则不会被分开

**检索逻辑**（`embeddings.worker.js:106-122`）：
```javascript
const scored = chunks.map((chunk, idx) => ({
  text: chunk.text,
  score: chunk.embedding ? cosineSimilarity(queryVec, new Float32Array(chunk.embedding)) : 0,
  index: chunk.index !== undefined ? chunk.index : idx
}));
scored.sort((a, b) => b.score - a.score);
return scored.slice(0, topK).filter(r => r.score >= CONFIG.similarityThreshold);
```

- 使用 `all-MiniLM-L6-v2` 模型进行语义检索，对中文字符的理解能力有限（英文训练模型）
- `topK=5`，返回最多5条结果
- 相似度阈值极低（`0.05`），几乎不会过滤掉任何结果

**答案生成**（`embeddings.js:185-201`）：
```javascript
results.forEach((r, i) => {
  const sourceLabel = docNames[i] ? `【来源: ${docNames[i]}】` : '';
  answer += `📄 **相关内容 ${i + 1}**（相似度: ${(r.score * 100).toFixed(0)}%）\n${sourceLabel}\n${r.text}\n\n`;
});
```

- 答案直接拼接所有检索到的 chunk 原文，不做任何筛选或总结
- 如果 topK=5 中混入了续签合同的内容，会全部展示给用户

**判定**: **有条件通过**

| 子项 | 结果 | 说明 |
|------|------|------|
| 场景分割正确性 | **通过** | 正则可正确匹配常见场景格式（`数字.数字`、`【场景】`） |
| 语义区分能力 | **风险** | `all-MiniLM-L6-v2` 是英文模型，对"新签"vs"续签"的语义区分可能不够精准 |
| 答案纯净度 | **风险** | topK=5 + 阈值0.05 导致可能返回相似度很低的匹配项，混入不相关内容 |

**问题描述**:
1. `similarityThreshold` 设为 `0.05` 过低，几乎形同虚设。语义不相关的内容只要包含个别相同字符，就可能通过阈值过滤。
2. `topK=5` 没有按场景去重逻辑。如果同一个文档中有3个 chunk 提到"合同"，可能占用大部分结果位，挤压其他精准匹配的空间。
3. `docNames` 数组使用结果索引 `i` 而非 chunk 原始索引 `r.index` 来获取文档名，当结果经过排序后索引不对应，可能导致来源标注错误。

### 场景2：相关但不同场景 - "如何续签合同"

| 项目 | 内容 |
|------|------|
| **测试目标** | 查询"如何续签合同"时，只返回"续签合同"相关内容，不返回"新签合同"内容 |
| **预期结果** | 检索结果全部与续签合同场景相关 |

**代码分析结果**:

- 与场景1共享同一套检索和答案生成逻辑
- `all-MiniLM-L6-v2` 模型将文本转为向量后，"新签合同"和"续签合同"在向量空间中的距离较近（共享大量字面特征），语义区分能力取决于训练数据
- 关键词降级搜索（`app.js:507-533`）使用精确子串匹配：查询"如何续签合同"会提取"如何续签合同"、"续签合同"、"续签"等关键词，只有同时匹配最多关键词的 chunk 才会排在前面
- 但由于评分公式为 `matchCount / keywords.length`，如果一个 chunk 包含"合同"但不包含"续签"，仍然能获得部分分数

**判定**: **有条件通过**

| 子项 | 结果 | 说明 |
|------|------|------|
| 关键词精准度 | **通过** | 多级关键词提取（完整词 + 2-4字子串）能较好匹配 |
| 排除干扰场景 | **风险** | 包含"合同"但不包含"续签"的 chunk 会获得低分但仍可能出现在结果中 |
| 向量语义区分 | **风险** | 英文模型对中文近义词的区分度有限 |

**问题描述**:
1. 关键词搜索没有"必须包含"逻辑。即使用户明确查询"续签"，包含"新签合同"的 chunk 如果也包含"合同"二字，仍可能获得分数。
2. 建议在关键词搜索中引入"否定词"或"必需词"概念，对于"如何续签合同"应要求结果必须包含"续签"。

### 场景4：相似度阈值测试 - 查询文档中不存在的内容

| 项目 | 内容 |
|------|------|
| **测试目标** | 查询一个文档中完全不存在的内容（如"如何申请年假"），系统应返回"未找到相关内容"的提示 |
| **预期结果** | 返回友好提示："抱歉，我在知识库中没有找到与'如何申请年假'相关的内容。请尝试：更换关键词搜索 / 联系管理员上传相关文档" |

**代码分析结果**:

**向量搜索阈值**（`embeddings.worker.js:121`）：
```javascript
return scored.slice(0, topK).filter(r => r.score >= CONFIG.similarityThreshold);
```

- `similarityThreshold: 0.05`，这是一个非常低的阈值
- 对于完全不相关的查询，`all-MiniLM-L6-v2` 模型通常仍会返回相似度在 0.0-0.2 之间的结果
- **如果没有任何 chunk 超过 0.05 阈值，向量搜索返回空数组**

**降级搜索**（`app.js:457-468`）：
```javascript
if (results.length === 0) {
  results = fallbackKeywordSearch(userMessage, allChunks);
}
if (results.length === 0) {
  results = fuzzySearch(userMessage, allChunks);
}
```

- 如果向量搜索返回空，会触发关键词搜索，然后是模糊搜索
- **模糊搜索**（`app.js:582-617`）的过滤阈值为 `score > 0.1`，但计算公式是 `Math.max(charScore * 0.3, wordScore * 0.7)`
- 对于"如何申请年假"这样的查询，如果知识库中有任何文档包含"年"或"假"字，模糊搜索就可能返回结果
- **这意味着几乎不可能触发"未找到相关内容"的提示**

**答案生成**（`embeddings.js:186-188`）：
```javascript
if (!results || results.length === 0) {
  return `抱歉，我在知识库中没有找到与"${userQuery}"相关的内容。\n\n请尝试：\n- 更换关键词搜索\n- 联系管理员上传相关文档`;
}
```

- 这段代码逻辑正确，但由于三级兜底搜索的存在，几乎不会被执行

**判定**: **失败**

| 子项 | 结果 | 说明 |
|------|------|------|
| 向量搜索阈值过滤 | **通过** | 逻辑正确，低于阈值的结果会被过滤 |
| 整体检索链路 | **失败** | 三级兜底搜索（向量->关键词->模糊）导致即使查询完全不相关的内容，也很可能返回结果 |
| 友好提示触发 | **失败** | 由于模糊搜索过于宽松，`results.length === 0` 几乎不可能成立 |

**问题描述**:
1. 三级兜底搜索的设计初衷是提高召回率，但代价是牺牲了精确度。对于完全不相关的查询，模糊搜索会强行返回低质量结果。
2. `fuzzySearch` 中 `score > 0.1` 的阈值过低。对于中文查询，只要有少量字符匹配就能超过此阈值。
3. 建议方案：
   - 为每级搜索设置不同的最低相似度/匹配度阈值
   - 在最终答案生成时检查最高分是否低于某个阈值，如果是则提示"未找到高度相关的内容"
   - 或者在 fuzzySearch 返回结果时标注为"模糊匹配，相关度较低"

### 场景5：答案质量测试

| 项目 | 内容 |
|------|------|
| **测试目标** | 检查答案是否为总结性内容、是否直接复制原文、步骤是否清晰 |

**代码分析结果**:

**答案生成逻辑**（`embeddings.js:185-201`）：
```javascript
function buildAnswer(results, userQuery, docNames = []) {
  // ...
  results.forEach((r, i) => {
    answer += `📄 **相关内容 ${i + 1}**（相似度: ${(r.score * 100).toFixed(0)}%）\n${sourceLabel}\n${r.text}\n\n`;
  });
  answer += `---\n💡 以上内容均来自知识库文档，如有疑问请查阅原始文档或联系管理员。`;
  return answer;
}
```

**分析**:

1. **是否为总结性内容**: **否**。答案直接拼接 chunk 原文（`${r.text}`），没有任何总结、归纳或改写。注释也明确说明"直接输出匹配的 chunk 内容"。

2. **是否直接复制原文**: **是**。每个结果都是原始 chunk 文本的完整复制。

3. **步骤是否清晰**: **取决于文档格式**。如果原文档有清晰的步骤编号（1. 2. 3.），则复制后步骤清晰；如果原文是段落式叙述，则步骤不清晰。

4. **答案格式问题**:
   - 相似度百分比显示为整数（`(r.score * 100).toFixed(0)`），精度不足，用户无法区分 10% 和 15% 的差异
   - 来源标注逻辑有 bug（`docNames[i]` 使用结果索引而非 chunk 索引，可能导致来源标注错误）
   - 所有结果平铺展示，没有按相关性分组或高亮关键词
   - 没有对冗余信息去重（如果两个 chunk 内容高度相似，会重复展示）

**判定**: **失败**

| 子项 | 结果 | 说明 |
|------|------|------|
| 答案是否为总结性内容 | **失败** | 直接拼接原文，无任何总结/改写逻辑 |
| 答案是否直接复制原文 | **是（问题）** | 100% 原文复制，用户体验差 |
| 步骤是否清晰 | **部分通过** | 取决于原文格式，系统本身不做步骤提取 |
| 来源标注准确性 | **失败** | `docNames[i]` 索引错误，可能导致来源标注不匹配 |
| 冗余去重 | **失败** | 无去重逻辑，相似 chunk 可能重复展示 |

**问题描述**:
1. 答案生成采用"原文搬运"模式，完全没有 LLM 总结或改写能力。注释提到"每个 chunk 已是一个完整场景"，但实际情况取决于分块效果。
2. 来源标注存在索引错位 bug：`results` 已经按相似度重新排序，但 `docNames` 数组仍使用排序后的索引 `i` 来取值。正确做法应使用 `r.index` 到 `chunkToDocMap` 中查找。
   - 相关代码在 `app.js:472`：`const matchedDocs = results.map(r => chunkToDocMap[r.index] || '未知文档');`
   - 但 `buildAnswer`（`embeddings.js:192`）中 `docNames[i]` 用的是结果序号 `i` 而非 chunk 原始索引，这两处逻辑不一致
3. 相似度显示为整数百分比，对于 5%-15% 区间的低分结果，用户看到的都是个位数，无法判断结果质量

## 三、分块策略深度分析

### 3.1 场景分割正则

```javascript
const scenePattern = /(?=\n\s*\d+\.\d+\s*【?场景】?|【场景】|\n\s*\d+\.\d+\s*)/;
```

| 正则分支 | 匹配目标 | 覆盖情况 |
|----------|---------|---------|
| `\n\s*\d+\.\d+\s*【?场景】?` | `1.1 【场景】xxx` 或 `1.1 场景xxx` | 严格匹配，覆盖面窄 |
| `【场景】` | 任何包含 `【场景】` 的行 | 覆盖面有限 |
| `\n\s*\d+\.\d+\s*` | `1.1 ` 或 `2.3 ` 开头的行 | 覆盖面较广，但可能过度分割 |

**问题**:
1. 第三分支 `\n\s*\d+\.\d+\s*` 过于宽泛，会将所有 `数字.数字` 格式的行作为分割点，即使这些行不是场景标题（如 `3.14` 这样的数据也可能被匹配）
2. 对没有编号或 `【场景】` 标记的文档，会降级为段落分块，此时场景边界丢失
3. 对 Markdown 格式的标题（`## 标题`、`### 标题`）没有识别能力，如果知识库文档使用 Markdown 格式，场景分割会失效

### 3.2 段落合并策略

```javascript
function mergeParagraphsIntoChunks(paragraphs, maxLength = 800) {
  // 按 maxLength=800 字符合并段落
}
```

- `maxLength=800` 对于中文场景来说，约等于 200-400 个中文字（加上标点和格式字符）
- 每个合并后的 chunk 可能包含 2-3 个段落
- **风险**: 如果两个不相关的段落恰好相邻（中间只有一个空行分隔），它们会被合并到同一个 chunk 中

## 四、检索链路深度分析

### 4.1 三级搜索策略

```
向量搜索 → 关键词搜索 → 模糊搜索
```

| 搜索级别 | 触发条件 | 阈值 | 特点 |
|----------|---------|------|------|
| 向量搜索 | 默认首选 | `score >= 0.05` | 语义匹配，但英文模型对中文支持有限 |
| 关键词搜索 | 向量搜索返回空 | `score > 0` | 精确子串匹配，要求至少一个关键词匹配 |
| 模糊搜索 | 关键词搜索返回空 | `score > 0.1` | 字符级匹配，极其宽松 |

### 4.2 核心问题

1. **没有"最终兜底阈值"**: 三级搜索各自有阈值，但没有任何一个"全局最低质量门槛"。只要模糊搜索返回了结果（哪怕相关度极低），就会被直接展示给用户。

2. **缺乏结果质量评估**: `buildAnswer()` 接收结果后不做任何质量检查，直接拼接输出。

3. **对话历史增强可能引入噪音**（`embeddings.worker.js:124-136`）：
   ```javascript
   enrichedQuery = `【对话背景: ${historyText}】当前问题: ${currentQuery}`;
   ```
   将对话历史拼接到查询中，如果历史对话涉及其他场景，可能影响当前查询的检索准确性。

## 六、优化建议

### 6.1 高优先级

1. **修复来源标注 bug**: 在 `buildAnswer` 中，使用 `r.index` 映射回原始 chunk 的文档名，而非使用结果序号 `i`。
   ```javascript
   // 修改前
   const sourceLabel = docNames[i] ? `【来源: ${docNames[i]}】` : '';
   // 修改后
   const sourceLabel = docNames[r.index] ? `【来源: ${docNames[r.index]}】` : '';
   ```

2. **提高相似度阈值**: 将 `similarityThreshold` 从 `0.05` 提高到 `0.15-0.2`，过滤掉明显不相关的结果。

3. **增加全局质量门槛**: 在 `buildAnswer` 或 `sendToAI` 中增加最终检查，如果所有结果的最高分低于某个阈值（如 `0.2`），直接返回"未找到高度相关的内容"提示。

### 6.2 中优先级

4. **答案去重**: 对返回的多个 chunk 进行相似度去重，避免重复展示内容高度相似的结果。

5. **增加答案总结能力**: 引入 LLM API 对检索结果进行总结和改写，而非直接拼接原文。

6. **优化场景分割正则**: 增加对 Markdown 标题（`##`、`###`）的识别，并收紧第三分支的正则以避免过度分割。

### 6.3 低优先级

7. **提高相似度显示精度**: 从整数改为保留1位小数（`toFixed(1)`）。

8. **关键词搜索增加必需词逻辑**: 对查询中的核心语义词设为"必需词"，结果必须包含必需词才计入匹配。

9. **模糊搜索增加最低字符匹配数**: 要求至少匹配查询中 50% 以上的不重复字符，避免过松匹配。

## 七、测试总结

| 测试场景 | 结果 | 通过/失败 |
|----------|------|----------|
| 场景1: 精准查询"如何新签合同" | 语义区分能力有限，存在混入其他合同场景的风险 | **有条件通过** |
| 场景2: 相关但不同场景"如何续签合同" | 关键词匹配基本正确，但缺乏排除干扰场景的机制 | **有条件通过** |
| 场景3: 无关查询"如何登录系统" | 登录场景独立性强，匹配效果较好 | **通过** |
| 场景4: 相似度阈值测试 | 三级兜底搜索导致"未找到"提示几乎无法触发 | **失败** |
| 场景5: 答案质量测试 | 直接复制原文，无总结/去重，来源标注有 bug | **失败** |

**整体评估**: 5个测试场景中，2个有条件通过，1个通过，2个失败。系统在基础检索功能上可用，但在答案质量、结果精度和边缘场景处理上存在明显不足。最关键的问题是三级兜底搜索过于宽松以及答案生成缺乏总结能力。
